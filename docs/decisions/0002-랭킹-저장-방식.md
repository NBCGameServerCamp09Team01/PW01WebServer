# 0002. 랭킹 저장 방식

- 상태: 채택(웹서버 `dev`에 PR 없이 들어감 10/12, 사후 리뷰. 마이그레이션은 `fix/ranking-migration-v8`에서 V7 → V8)
- 날짜: 2026-10-12
- 결정: Sang-Hyun-Kim(랭킹 담당). 명세는 루트 `docs/contracts/ranking-api.md` v1, `redis-keys.md` v1.3 랭킹 절

## 배경

- 랭킹은 "Redis 실시간 + DB 영구를 동시에"(10/11)로 정했다. 순위의 원천은 서버가 받아들인 클리어 결과다.
- 보드는 스테이지·지역·전체 총합·진행 네 가지, 진행을 뺀 셋은 전체 기간 + 주간이다. 순서는 점수 → 먼저 달성 → 먼저 기록이다.

## 결정

| 번호 | 항목 | 결정 |
|---|---|---|
| R01 | 원천 | MySQL 랭킹 표 5개(V8, 처음 V7에서 S4와 겹쳐 옮김): `ranking_clear_log`(클리어마다, 덧붙이기만, `clear_seq` = 기록 순번), `stage_best_record`·`region_best_score`·`total_best_score`·`account_clear_progress`(계정당 한 줄, 오를 때만 덮어씀) |
| R02 | 결과 표와의 관계 | 결과 표(`stage_play_result`, S2)는 바꾸지 않고 외래 키도 걸지 않는다. 랭킹이 자기 표에 순번·점수를 갖는다(S2와 병합 순서에 묶이지 않음, 단독 시험) |
| R03 | 쓰기 시점 | 결과를 저장하는 트랜잭션 안(`RankingRecordService.recordClear`, `MANDATORY`). Redis는 커밋 뒤 이벤트(`@TransactionalEventListener(AFTER_COMMIT)`)로 고친다 |
| R04 | 쓰기 방법 | JPA 엔티티 없이 `JdbcClient` SQL. "점수가 클 때만 덮어씀"을 `INSERT … ON DUPLICATE KEY UPDATE` 한 문장으로(동시 저장에도 어긋나지 않음). 결과 저장 쪽 영속성 컨텍스트를 건드리지 않는다 |
| R05 | Redis 모양 | ZSet 점수 = −보드 점수, 멤버 = `<달성 ms 13자리>:<순번 20자리>:<계정 ID>:<상세>` + 계정 → 멤버 해시. 갱신·조회·다시 채우기는 Lua 6개 |
| R06 | 어긋남 | Redis 갱신이 실패하면 그 서버 메모리에 "다시 채울 보드" 표시 → 다음 조회 때 MySQL에서 다시 채움. 보드가 없으면(만료·삭제·새 주) 다시 채움. 다시 채우는 중 커밋된 기록은 임시 보드에도 들어간다 |
| R07 | 장애 | 랭킹 Redis 명령만 실패하면 MySQL로 같은 답(값 커서라 두 길의 커서가 같다). Redis 전체 장애는 인증에서 503 |
| R08 | 커서 | 순위 번호가 아니라 마지막 줄 값(키셋). DB는 순위 인덱스 range, Redis는 같은 값으로 시작 위치 |
| R09 | 전체 보드 수명 | 30일(고칠 때마다 다시). 운영 Redis가 "만료 있는 키부터 지움" 정책일 때 세션 키보다 랭킹 키가 먼저 밀리게 |

## 실행 계획 비교(② 최고 기록 표 vs ① 매번 묶기)

시험 DB(MySQL 8.4.11)에 계정 1만·클리어 5만(스테이지 둘)을 넣고 잰 값. 다시 재려면:

```bash
PW01_RANKING_EXPLAIN=true ./gradlew test --tests '*RankingExplainTest'   # build/ranking-explain.txt
```

| 쿼리 | 계획 | 실제 시간 |
|---|---|---|
| ② 첫 묶음 20줄(`stage_best_record`) | `ix_stage_best_record_rank` index lookup → Limit. **정렬 없음** | 0.4ms |
| ② 커서 다음 묶음 | 같은 인덱스 range scan(펼친 커서 조건이 range 셋으로) | 0.24ms |
| ② 내 순위(앞에 있는 줄 수) | PRIMARY lookup + filter(5천 줄 읽음) | 0.9ms |
| ① 첫 묶음(`ranking_clear_log`에서 계정별 최고를 매번) | index lookup → **정렬 + 창 함수 + 임시 표** → 정렬 | 32ms |
| 주간 첫 묶음(이번 주, `ranking_clear_log`) | **표 전체 읽기**(이번 주가 기록의 35%라 옵티마이저가 인덱스를 버림) → 정렬 + 창 함수 | 26ms |

- ②가 ①보다 약 80배 빠르고, ①은 클리어가 쌓일수록 느려진다(정렬·창 함수가 그 스테이지의 모든 클리어를 읽음). 그래서 전체 기간은 ②를 원천으로 둔다.
- 주간은 ①과 같은 방식이지만 Redis가 평소 길이고, MySQL은 보드가 없을 때(주에 한 번 다시 채우기)와 부분 장애 때만 읽는다. 기록이 많아지면 주간 최고 기록 표(계정 × 스테이지 × 주)를 더하는 것이 다음 단계다.
- 내 순위 COUNT는 PRIMARY로 읽었다(순위 인덱스 range가 아님). 지금 규모에서는 1ms 안이라 두고, 계정이 많아지면 인덱스 힌트나 Redis 길(ZRANK)만으로 충분한지 다시 본다.

## 대가(알고 고른 것)

- 결과 저장 트랜잭션에 쓰기가 3~5문장 늘어난다(클리어일 때만).
- "다시 채울 보드" 표시는 서버 메모리라 서버가 다시 뜨면 사라진다(만료·키 삭제 때까지 기록 하나가 빠질 수 있음). 확장: 아웃박스 표.
- 점수는 기록할 때의 권장 클리어 시간으로 계산해 저장하고 다시 계산하지 않는다.

## 다시 볼 때

- 계정·클리어가 늘어 주간 MySQL 읽기가 느려질 때(주간 최고 기록 표)
- 서버가 여러 대가 될 때(실패 표시를 공유: 아웃박스)
- 난이도가 게임에 들어올 때(점수 배수 `RankingScore.difficultyMultiplierPercent`, 보드 나누기)
